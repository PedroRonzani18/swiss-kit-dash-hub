# Swiss Kit Pipeline

This directory stores handoff artifacts for Codex-assisted development runs.

The goal is not to let AI code freely. The goal is to keep planning, implementation and review separated and auditable.

The canonical order is:

```text
Planner -> human approval -> Coder -> Tester -> Reviewer
```

The project skill at `.agents/skills/ship/SKILL.md` is the executable source of truth:

```text
$ship start <request> [--run-id <id>]
$ship resume <run-id>
```

`start` creates a fresh run and stops after planning. `resume` in `awaiting-approval` explicitly approves the current spec when it has no `OPEN QUESTIONS`.

## Structure

```text
.pipeline/
  README.md
  runs/
    <run-id>/
      request.md
      context.md
      spec.md
      changes.md
      test-results.md
      review.md
      review-attempt-1.md
      state.json
```

`review-attempt-1.md` exists only when a correction cycle occurs.

## Files

### `request.md`

Original user request.

### `context.md`

Repository context found by the Planner:

- relevant files
- existing patterns
- commands
- architecture notes
- risks

### `spec.md`

Implementation spec generated by the Planner.

Must include:

- objective
- in scope
- out of scope
- files likely to change
- acceptance criteria
- edge cases
- validation commands
- risks
- open questions, if any

### `changes.md`

Implementation summary generated by the Coder.

Append a labeled section for each implementation attempt. Do not replace earlier attempts.

Must include:

- files changed
- behavior changed
- tests added or updated
- validation commands
- known risks

### `test-results.md`

Required validation record generated by the Tester.

Append a labeled section for each validation attempt. Record commands that ran, pass/fail status, relevant failures, omitted commands and remaining risk. Do not remove earlier failures after a correction.

### `review.md`

Read-only review generated by the Reviewer.

Must end with:

- `VERDICT: SHIP`
- `VERDICT: NEEDS WORK`
- `VERDICT: BLOCK`

When the first verdict is `NEEDS WORK`, archive this file as `review-attempt-1.md` before the second Reviewer run. The current `review.md` must contain exactly one current verdict.

### `state.json`

Pipeline state maintained by the orchestrator:

```json
{
  "version": 1,
  "runId": "<run-id>",
  "status": "planning",
  "attempt": 0,
  "lastVerdict": null,
  "updatedAt": "<ISO-8601 UTC>"
}
```

Allowed statuses:

- `planning`
- `awaiting-approval`
- `implementing`
- `testing`
- `reviewing`
- `needs-work`
- `blocked`
- `ready-for-human-review`

Approval starts attempt 1. The single allowed correction cycle uses attempt 2.

## Outcome rules

- Planning always stops for explicit human approval.
- `OPEN QUESTIONS` must be resolved in the spec before approval.
- `SHIP` produces `ready-for-human-review`.
- `BLOCK` stops immediately.
- The first `NEEDS WORK` allows one Coder -> Tester -> Reviewer correction cycle.
- A second `NEEDS WORK` stops and returns control to the human.
- A finding that changes scope returns to Planner and requires a new approval.

## Git policy

Generated run folders should not be committed.

Keep only:

```text
.pipeline/README.md
.pipeline/runs/.gitkeep
```

Ignore:

```text
.pipeline/runs/*
!.pipeline/runs/.gitkeep
```

## Human approval

The pipeline does not approve its own work.

A human must review the diff and decide whether to commit, push or merge.
